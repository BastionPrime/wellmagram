# wellmagram v1-max — план первой версии (Telegram + MAX)

Дата: 2026-10-03
Тикет: OPE-3778 (дочерний к OPE-2270)
Основание: решение владельца от 02.10 (записано adm в OPE-2270, комментарий
a8f686f3): **MAX входит в v1 сразу**, вариант «v1 только Telegram» отклонён.
Предыдущий артефакт `/srv/dev/OPE-3403/v1-plan.md` (Telegram-only, V1–V8,
19 кал.дн.) этим планом заменяется, а не расширяется.

База: main = 86d5004 (= 33141ba + docs-only ADR-0002), ядро Фаз 1–2 готово
(модель аккаунтов, SessionManager, TdBridge на швах, MaxBackend на швах,
foreground-сервис + NotificationCenter, debug-APK v0.1.0-debug).

## 0. Что уже есть (не оценивается)

- Аккаунты: `AccountRegistry`, `CredentialStore` (secure-storage-шов),
  спуф-профили (`SpoofProfileStore`), сеть = MAX | Telegram.
- Telegram: `TdBridge` на шве `TdClientLike` (+ живой FFI-адаптер
  `TdFfiClient`, libtdjson arm64 в jniLibs), `TdAuthFlow` (телефон → код →
  2FA, state-машина готова), `TdChatStore`, `TdMessages`, `TdSessions`
  (per-account TdClientConfig, каталоги `tg/<id>`), `TdGhost`, `TdPush`
  (шов, `TdPushNoop` до ADR-0002).
- MAX: `MaxBackend` реализует `MessengerBackend` поверх шва `MaxApiLike`;
  SessionManager (switch/parallel) для MAX-сессий; антибан-rate-limiter,
  мапперы push-пакетов → `BackendEvent`.
- Общее: `Capabilities` (UI не ветвится по сети), `NotificationCenter`
  (не знает источник события — п.2.5), `ConnectionForegroundService` (Kotlin,
  FGS remoteMessaging) + `ConnectionServiceController` (Dart).
- 308 unit-тестов зелёные, gitleaks 0.

Чего НЕТ: UI (плейсхолдер), живой MAX-транспорт (kolibri/Api за `MaxApiLike`
не подключён к продакшн-реализации), вход MAX (token-флоу),
интеграционные прогоны на устройстве, push-доставка.

## 1. Скоуп v1-max (результат)

Приложение на одном Android-телефоне (arm64), в котором:

- вход в Telegram: телефон → код → 2FA (один номер с 2FA обязателен к
  проверке, путь не блокирует);
- вход в MAX: по токену (продакшн-путь входа MAX — token-auth;
  телефон/QR/сборка аккаунта — вне v1);
- список чатов и экран переписки для обеих сетей через единый
  `UnifiedChat`-контракт (Capabilities уже декларирует различия: у TG в v1
  нет медиа, у MAX — всё из шва `MaxApiLike`);
- переключение аккаунтов (switch-режим SessionManager) + минимум двух
  одновременных аккаунтов (1 TG + 1 MAX);
- отправка/получение текста, реакции, правки/удаление — в рамках
  Capabilities каждой сети;
- фоновая работа: ConnectionForegroundService держит живые соединения,
  NotificationCenter показывает входящие (baseline = foss/FGS по ADR-0002;
  google-flavor/FCM в v1 НЕ входит);
- ghost-режим и спуф-профиль остаются включёнными по умолчанию (решение
  владельца: механики в дереве, репо публично).

Вне скоупа v1: звонки, медиа в TG, webpush, мульти-parallel-сессии всех
аккаунтов сразу, Google Play-подготовка, релицензирование.

## 3. Календарная оценка

Ограничения из вводных: тестовое устройство ОДНО (arm64), один комплект
номеров → живая приёмка сериализуется; ревью раз в день (замеренный
регламент Фаз 1–2).

Критический путь при двух инженерах (параллель: инженер-1 ведёт MAX-линию
M1→M2→(частично S1), инженер-2 — UI-линию U1→U2→U3→U4, затем A1):

| Неделя | Инженер-1 | Инженер-2 |
|--------|-----------|-----------|
| Д 1–3 | M1 MAX-транспорт | U1 каркас + U2 список чатов |
| Д 4–5 | M2 вход MAX | U3 экран чата |
| Д 6–7 | стык M2+U4, ревью/фиксы | U4 переключатель, ревью/фиксы |
| Д 8–9 | [WAIT-KEYS] A1 (если ключи пришли; иначе смещение) | A1/A2-поддержка, стыковка |
| Д 10 | S1 сборка + сквозная приёмка (оба) | S1 |
| Д 11 | запас на ревью-итерации | запас |

**Итого: 11 рабочих дней до готовой v1-max при наличии ключей к Д 8
(буфер +1 день); Telegram-only-оценка 19 дн. непригодна — MAX-ядро уже
в дереве (MaxBackend/Capabilities/SessionManager готовы), добавка MAX =
живой транспорт M1 и вход M2, а не второе приложение.**
Если ключи задерживаются сверх Д 8 — A1/A2 сдвигают финиш день-в-день,
остальной план не перестраивается (A-блок изолирован).

Сравнение с 19 дн. Telegram-only (OPE-3403): та оценка строилась до
решения о MAX и включала «двухшаговый» вход TG с нуля; здесь ядро
SessionManager/Capabilities уже общее, поэтому пересчёт = MAX-транспорт (3)
+ вход (2) + интеграционные стыки, а не сумма двух планов.

## 4. Риски

1. **Ключи api_id/api_hash не переданы** (обещаны 02.10) — блокирует A1/A2;
   смягчение: A-блок изолирован файлово, остальной план идёт; при задержке
   >3 дней эскалация владельцу через adm-dev-lead. Значения ключей нигде не
   печатаются и не попадают в тикет/чат/код (только секрет-контур доски).
2. **kolibri-интеграция M1 сложнее шва** — upstream-модули (Flutter
   plugins) не импортируются в pure-Dart workspace; та же проблема решена
   для TDLib через FFI-адаптер, для MAX может потребоваться shim-слой.
   Смягчение: шов `MaxApiLike` уже узкий; при провале — сокращение скоупа
   MAX-функций до sendText/markRead с явным ADR.
3. **Одно тестовое устройство** — сериализует живую приёмку (A2/S1);
   частично закрывается mock-гейтами в CI-подобных прогонах (образ
   wellmagram-builder).
4. **Антибан/спуф-механики в публичном репо** — принято владельцем (п.5
   решения); риска для плана нет, но любое изменение спуф-логики должно
   проходить ревью как security-чувствительное.
5. **FCM-only код** — запрещён п.2.5 (NotificationCenter не знает источник
   события); риск закрыт архитектурно, упомянуто для ревьюеров.
