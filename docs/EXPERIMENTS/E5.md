# E5 — MAX parallel sessions soak (methodology)

> Status: **methodology only — NOT run yet.**
> The 48 h soak itself runs only after the owner decides on two throwaway
> MAX test accounts and a dedicated device (see Preconditions).
> This file exists so any engineer can run E5 without further questions.

## 1. Purpose

Answer decision **B3**: does `SessionMode.parallel` (all MAX accounts holding
live sessions at once) go into 1.0, or does 1.0 ship switch-mode only?

Parallel mode is implemented in `lib/core/app/session_manager.dart`
(`SessionMode.parallel`, ADR-0003 gate) but is not exercised against the live
MAX transport for two accounts over a long window. E5 is the measurement that
closes that gap.

Concretely, E5 must produce numbers for:

- session stability — disconnect/reconnect counts per account over 48 h;
- reconnect behaviour — whether re-arms self-heal and how long a full
  reconnect takes;
- ping/latency — distribution of ping round-trips per account;
- battery — parallel vs switch energy cost (Battery Historian);
- antiban sanity — phone-lookup limiter and spoof-profile separation behave
  under a long run (no shared-profile or shared-queue artifacts).

## 2. Preconditions

⛔ **Gate: none of the steps below start until the owner (plan owner) has
approved two disposable MAX test accounts and a dedicated test device.** The
accounts must be throwaway — a 48 h parallel soak on a personal account is an
acceptable risk only for its owner, not for this experiment.

1. **Two disposable MAX test accounts** (A and B), phone-registered, already
   paired with the app, each with a fresh credential set in the app's
   `CredentialStore`. Owner decision required — the experiment does not
   create accounts itself.
2. **Dedicated Android device** (physical, not emulator — battery numbers
   from an emulator are meaningless): Android 8+, arm64-v8a, USB debugging
   enabled, no other heavy apps running, screen-off policy enabled for the
   soak window (see §5 step 6).
3. **Debug build** of the app on the branch under test:
   `flutter build apk --debug` (includes `libtdjson`; see README Build & test).
4. **Distinct spoof profiles** for A and B. The store already excludes
   device models used by other accounts
   (`SpoofProfileStore.generate(usedDeviceNames:)` in
   `lib/core/storage/spoof_profile_store.dart`) — verify before the run that
   `A.deviceName != B.deviceName` and that timezone/locale/timezone pairs
   differ where the preset table allows (plan 4.8: different spoof profiles
   per account). If both profiles collide, regenerate B's profile.
5. Host tooling on the workstation: `adb`, `bugreport` processing (Battery
   Historian `historian` / `battery-historian` binary), Python 3.
6. A log-capture plan is in place (§4) — decide up front where the run log
   goes (host file per §5 step 5) so nothing is invented mid-run.

- Branch: the feature branch under review (one branch = one change).
- Baseline for comparison: the same commit with `SessionMode.switchMode`

## 4. What to log

Two sources, both mandatory:

### 4.1 In-app event stream

Subscribe during the harness run (§5 step 3) and write one JSON line per
event to the run log:

- `BackendEventKind.connected` / `disconnected` per account
  (`Stream<BackendEvent> events` on `MessengerBackend`, mapped through
  `MaxBackend`'s event controller) → the disconnect/reconnect ledger;
- `BackendState` transitions per account
  (`Stream<BackendState> stateChanges`: `connecting / online / paused`) →
  reconnect duration (time between `disconnected`→`online` pairs);
- ping/latency: log each ping round-trip observed on the MAX seam
  (`pingIntervalSecs`, default 30 s, in
  `lib/core/backends/max/max_api_seam.dart`) — timestamp sent/received;
  if the seam does not yet surface RTT to Dart, record the per-account
  event gap as a proxy and mark the field `rtt=proxy` in the log;
- `AntibanRateLimiter` status events (`statusStream` in
  `lib/core/backends/max/antiban_rate_limiter.dart`) — every queued request
  and its wait, to confirm the two accounts never share a burst budget
  unexpectedly;
- UTC wall-clock timestamp on every line (device clock, `DateTime.now()`).

Line shape (one JSON object per line, `jq`-friendly):

```json
{"ts":"2026-11-01T09:00:00.123Z","account":"max:<id>","kind":"state","from":"online","to":"disconnected"}
{"ts":"2026-11-01T09:00:07.456Z","account":"max:<id>","kind":"ping","rtt_ms":412}
{"ts":"2026-11-01T09:00:09.000Z","account":"max:<id>","kind":"ratelimit","queued":false,"remaining":19}
```

### 4.2 Device-side (Battery Historian)

- `adb shell dumpsys batterystats --reset` before the soak window;
- `adb bugreport` at T+48 h;
- `historian` on the bugreport → battery drain per hour, wakelocks per
  process (the MAX transport + the app), radio (mobile/wifi) active time —
  the two live sockets vs one is the expected measurable difference.

## 5. Steps

All steps assume the preconditions in §2 are met and the owner has said go.

1. Confirm distinct spoof profiles (§2 step 4) and record them in the
   protocol (device model, os version, timezone — not the raw `device_id`).
2. Install the debug APK on the test device; log in to A and B.
3. Start the in-app harness with `SessionMode.parallel`:
   `SessionManager(mode: SessionMode.parallel, factory: ...)`; call
   `start()` for A then B; both backends must report `online`.
   Subscribe all streams from §4.1 to the run log before `start()` returns.
4. Reset battery stats (`dumpsys batterystats --reset`) and note the start
   time (UTC) and device battery %.
5. Run **48 h**. Log capture: forward the run log to the host periodically
   (`adb pull` or `adb logcat` capture) so a device reboot does not lose the
   full ledger. Check in at least every 12 h: both accounts still `online`,
   log still growing, device charging policy unchanged (§5 step 6).
6. Device policy for the window: screen-off (background soak is the
   scenario parallel mode targets), stationary, wifi preferred with mobile
   as failover (note which transport was active in the protocol), battery
   not plugged unless the run is a no-drain variant — record the choice.
7. Baseline run: repeat steps 2–6 with `SessionMode.switchMode` on the same
   commit, same device, same window length. Without the switch baseline the
   battery and reconnect numbers have no comparator.
8. At T+48 h: pull the log, take `adb bugreport`, run Battery Historian,
   compute the metrics below, fill the protocol (§7).
9. While the run is live, do not interact with the app beyond the 12 h
   checks; any manual intervention goes into the protocol as a run event.

## 6. B3 decision criteria (measurable)

All criteria are computed from the run log and the two Battery Historian
reports; the decision template is:

- **Parallel enters 1.0** iff, over 48 h per account:
  - self-healed disconnects: ≥ 90 % of `disconnected` events return to
    `online` without manual intervention, and no account is offline more
    than 60 min cumulative;
  - reconnect time: median full reconnect ≤ 10 s, p95 ≤ 30 s (from
    disconnected→online gap pairs);
  - ping/latency: median RTT (or proxy) ≤ 500 ms and p95 ≤ 1500 ms in
    parallel, and parallel RTT does not exceed the switch baseline by more
    than 20 % on either percentile;
  - battery: parallel drain exceeds the switch baseline by no more than
    15 % relative over the same window (screen-off, both runs);
  - antiban: zero cross-account profile collisions in the log (no
    shared `deviceName` warnings, both rate-limit streams show
    account-separated bursts), and no account ends the run rate-limited or
    banned (login still valid at T+48 h).
- **Parallel stays out of 1.0** if any criterion fails; the failing
  criterion(s) and the measured numbers go into the protocol, and the
  follow-up issue references them.
- Thresholds are the plan's decision anchors; if the owner wants different
  numbers, the change lands here before the run, not after.
