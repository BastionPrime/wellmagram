# ADR-0002: push-стратегия — дерево решений по исходам E1/E2/E4

Дата: 2026-10-02
Статус: **proposed** (каркас; активируется исходами E1/E2/E4, уточняется E7)
План: docs/plan-v3.md §3.4 (проверенные факты), §4.6 (уведомления и фон), §4.6.3
(webpush-кандидат), Т-0.4/Т-0.5/Т-0.7/Т-0.10 (E1/E2/E4/E7), раздел 9 (В1)
Код: lib/core/backends/telegram/td_push.dart (шов push-регистрации),
lib/core/notifications/notification_center.dart (единая точка уведомлений)

## Контекст

План v3 требует зафиксировать push-стратегию до Т-2.10 (Фаза 2, push
TelegramBackend): «Т-2.10 push — по ADR-0002 (включая webpush-опцию E7)»
(plan §Фаза 2). Исходы трёх экспериментов Фазы 0 являются входами решения:

- **E1** (Т-0.4) — MAX-пуш под собственный package: google-services.json
  проекта max-messenger-app с нашим package_name, проверка токена, Opcode.config
  без WRONG_DEVICE_TOKEN, доставка при убитом процессе, стабильность 24 ч,
  ⛔ STOP.
- **E2** (Т-0.5) — Telegram-пуш: собственный Firebase-проект или конфигурация
  официального Telegram, ⛔ STOP.
- **E4** (Т-0.7) — два sender ID (0.5 д).

Код уже канало-агностичен по построению (решение владельца: код, где FCM —
единственный путь доставки, блокируется на ревью):

- `td_push.dart` швом `TdPushToken` (channelId + builder wire-формы) не
  выбирает канал; `TdPush.register` отправляет `registerDevice` c
  DeviceToken-конструктором, который передаёт вызывающий. Три
  schema-проверенных конструктора уже существуют: `deviceToken
  FirebaseCloudMessaging` (8389: token, encrypt), `deviceTokenWebPush` (8410:
  endpoint, p256dh_base64url, auth_base64url), `deviceTokenSimplePush` (8412:
  endpoint).
- `MessengerBackend.registerPush` — контракт без привязки к каналу; сегодня
  для Network.telegram он разрешается в `TdPushNoop` («регистрация —
  no-op/шов до ADR-0002», Т-2.10).
- `NotificationCenter` не знает источник события: FGS+живое соединение, FCM
  или webpush приходят как одинаковые BackendEvent (notification_center.dart:
  7-10).

## Базовое решение (не зависит от исходов E1/E2/E4)

**Baseline = flavor `foss` + foreground-сервис.** `ConnectionForegroundService`
(Kotlin, тип FGS `remoteMessaging`, targetSdk ≥ 34; fallback `dataSync`),
background Flutter engine (FlutterEngineCache), BOOT_COMPLETED-автостарт,
реконнект с экспоненциальной задержкой, запрос исключения из оптимизации
батареи — уже в кодовой базе (Т-1.9, план §4.6). Любая ветка дерева ниже
НАДСТРАИВАЕТ этот baseline, никогда не заменяет его: foss-сборка имеет
доставку с первого дня (живое соединение из FGS), google-flavor — опция
поверх.

(MAX/Telegram); `+` = эксперимент пройден, `−` = провален/STOP, `—` =
не запускался.

E7 (Т-0.10, мини-разведка webpush-слоя) не является входом активации — он
уточняет любую ветку: (а) пригодность webpush как базовой доставки
foss-сборки без FCM (усиление веток 1/5), (б) дополнение к FCM в google
(ветки 2/3/4/6: webpush wss из FGS как резервный канал при недоступности
FCM), (в) требования к фону (Doze-жизнеспособность wss-сокета, рестарт
webpush из FGS — Т-4.3 «интеграция webpush-канала в политику доставки»).
Результат E7 → docs/experiments/E7.md → reopen этого ADR (уточнение
флavor-плана, смена статуса proposed → accepted).

## Механизм замены (код не меняется при любом исходе)

Смена no-op → реальный канал = замена внедряемого объекта в DI, интерфейс
сохраняется: `TdPushNoop` → `TdPush` с билдером выбранного конструктора
(`tdFcmDeviceToken` / `tdWebPushDeviceToken` / `tdSimplePushDeviceToken`,
все три уже schema-проверены, test/td_push_test.dart). Решение владельца п.2.5
остаётся в силе: код, где FCM — единственный путь доставки, блокируется на
ревью; равноправие трёх каналов сохраняется до активации ветки.

## ⛔ Решение владельца (В1, план §9) — НЕ разрешено этим ADR

Использование Firebase-конфигурации официального MAX (E1) и/или официального
Telegram (E2) в flavor `google`; webpush-канал (E7) как без-FCM альтернатива —
приоритет между FCM и webpush в google-сборке. В1 — открытый вопрос
⛔ до старта соответствующих фаз: положительные E1/E2/E4 НЕ означают
разрешение брать чужие конфигурации; ветки 2–4 и 6 таблицы активируются
только после явного решения владельца по В1 (карточка на доске, владелец
продукта). До решения В1 любые варианты конфигураций считаются доступными
только для экспериментов E1/E2 (STOP-гейт), не для пользовательских сборок.

## Последствия

- Т-2.10 (Фаза 2) не блокируется: seam уже готов, wiring = замена
  no-op-объекта; активация — по ветке таблицы после E1/E2/E4 (+В1).
- Т-4.3 (google flavor, 3–4 д) запускается только если ADR-0002 разрешает
  (ветки 2–4/6) — план §Фаза 4.
- C2-критерий доставки (план §Фаза 4): foss — ≤ 10 с (FGS/webpush/живое
  соединение), google — ≤ 5 с где FCM работает по E1/E2/E7.
- SECURITY.md v0 (после E6): при активации google — в белый список S1
  добавляются FCM/GMS-хосты (только flavor `google`, инвариант S4: в foss
  Firebase отсутствует полностью).

## Ограничения

- E1/E2/E4/E7 ещё не выполнены (Фаза 0 не начата): все ветки таблицы —
  преждевременная фиксация их исходов, активации требует фактических
  результатов из docs/experiments/.
- Live-регистрация на реальном TDLib и валидация deviceTokenWebPush-ключей
  (p256dh/auth) отложены до сборочного образа ADM — как и вся Фаза 2
  (живая часть); настоящий ADR фиксирует только стратегию выбора.
- Таблица не покрывает частичные комбинации E7 (webpush работает, но только
  в foss) — ветка уточняется reopen-ом по факту E7.
